# Project spec: Notes to Questions

Build guide for Claude Code. This file describes **what** to build and **how it should behave and look**. It contains no implementation code on purpose: write the code from this spec.

Owner: Abdulrahman Mawlood · AI course midterm project · Supervisor: Prof. Dr. Ismail Abdulrahman
Deadline: 2 days. Prefer working and simple over complete and clever.

---

## 1. What the product is

A website where anyone pastes their study notes and gets quiz questions generated by a **fine-tuned T5 Transformer**. Every question is checked automatically for:

- **Relevance:** is the question about the notes?
- **Correctness:** can the notes actually answer it, with the intended answer?

The project is graded as an AI project, so the website must make the model's work **visible**: which answer the model was asked about, how relevant each question is, and whether a separate model could answer it.

### Users

- A student pasting lecture notes to quiz themselves.
- The teacher watching a live demo.

### Out of scope (do not build)

- Accounts, login, sign-up, sessions
- A database or saved history on the server
- Payments, sharing links, multi-language UI
- Any training code in this repo (training lives in the Colab notebook)

## 2. System overview

```
┌────────────────────┐      HTTPS / JSON       ┌──────────────────────────────────────┐
│  React website     │  ───────────────────▶   │  FastAPI service                     │
│  (Vite + Tailwind) │   POST /generate        │                                      │
│  runs on laptop    │   GET  /health          │  1. split notes into sentences       │
│  localhost:5173    │  ◀───────────────────   │  2. pick candidate answers (spaCy)   │
└────────────────────┘   questions + scores    │  3. generate questions (fine-tuned T5)│
                                               │  4. relevance (MiniLM embeddings)    │
                                               │  5. correctness (DistilBERT QA)      │
                                               │  6. filter, rank, verdict            │
                                               └──────────────────────────────────────┘
                                                 runs in Google Colab (GPU) behind a
                                                 Cloudflare quick tunnel, or locally on CPU
```

Three models, three jobs. Keep them separate; the checkers must never be the generator.

| Model | Job | Source |
|---|---|---|
| Flan-T5-base, fine-tuned on SQuAD | writes the questions | `MODEL_DIR` (folder saved by the Colab notebook, e.g. on Google Drive) |
| `sentence-transformers/all-MiniLM-L6-v2` | relevance score | HuggingFace |
| `distilbert-base-cased-distilled-squad` | correctness check | HuggingFace |

## 4. API contract (must match exactly)

The existing Colab notebook already serves this contract. The repo API must be a drop-in replacement, and the website must work with either.

### `GET /health`

Response `200`:
```
{ "status": "ok", "model": "<short description>", "device": "cuda" | "cpu" }
```

### `POST /generate`

Request body:
```
{ "notes": string (20 – 12,000 chars), "num_questions": integer (1 – 15, default 5) }
```

Response `200`:
```
{
  "questions": [
    {
      "question":      string,   // ends with "?"
      "answer":        string,   // the span the model was asked about
      "context":       string,   // the source sentence containing the answer
      "relevance":     number,   // 0–1, rounded to 3 decimals
      "correctness":   number,   // 0–1 token F1 between QA answer and intended answer
      "qa_answer":     string,   // what the QA model answered
      "qa_confidence": number,   // 0–1
      "verdict":       "good" | "check" | "weak"
    }
  ],
  "summary": {
    "count":         integer,
    "avg_relevance": number,
    "pct_correct":   number,     // % of questions with correctness ≥ 0.5
    "seconds":       number      // server-side generation time
  }
}
```

Errors:
- `422` validation (FastAPI default shape). The website must turn it into a readable sentence.
- `500` with `{ "detail": "<message>" }`.

CORS: allow all origins (the site runs on localhost and calls a tunnel URL).

## 5. API behaviour: the pipeline

`questionsFromNotes(notes, numQuestions)` runs these steps in order. Each step is a pure function except the model calls.

1. **Clean and split.** Collapse whitespace. Split into sentences on `. ! ?` followed by a space and a capital letter or digit. Drop sentences under 4 words.
2. **Candidate answers.** For each sentence, use spaCy `en_core_web_sm` to collect named entities, then noun chunks. Keep spans of 1–6 words, longer than 2 characters, not pronouns (`it, they, this, that, these, those, he, she, we, you, i, them, which, who, what`), no duplicates (case-insensitive). Strip surrounding punctuation.
3. **Spread across the notes.** Round-robin: first candidate of every sentence, then the second of every sentence, and so on, until you have `2 × numQuestions` picks. This stops all questions coming from the first paragraph.
4. **Generate.** For each pick, build the model input exactly as in training:
   `generate question: <previous sentence> <sentence with "<hl> answer <hl>" around the answer> <next sentence>`
   Generate in batches with beam search (4 beams, max 48 new tokens). Use `torch.no_grad()`.
5. **Score.**
   - Relevance: cosine similarity between the question embedding and the embedding of its sentence window (previous + current + next sentence).
   - Correctness: run the QA model with the question over the **whole** notes; token F1 between its answer and the intended answer (lowercase, strip punctuation and the articles a/an/the).
6. **Filter, rank, verdict.**
   - Drop questions that don't end in `?` and duplicates (case-insensitive).
   - Verdict: `good` if correctness ≥ 0.5 **and** relevance ≥ 0.4; `check` if exactly one holds; `weak` if neither.
   - Sort: correct ones first, then by relevance descending. Return the first `numQuestions`.
   - Build `summary`. Time the whole call.

### Model loading

- Load all three models **once at startup**, not per request. `/health` should only report `ok` after loading finished.
- Device: CUDA if available, otherwise CPU. Must work on CPU (slower is fine, roughly 5–15 s per request for 5 questions).
- `MODEL_DIR` comes from an environment variable. Fail at startup with a clear message if the folder has no `config.json`.

### Running it

- **Colab (demo default):** `run_colab.ipynb` mounts Drive, installs `requirements.txt`, starts uvicorn on port 8000 in a background thread, starts a Cloudflare quick tunnel (`cloudflared tunnel --url http://localhost:8000`), and prints the `https://*.trycloudflare.com` URL in large, obvious text.
- **Local fallback:** `MODEL_DIR=./qg-flan-t5 uvicorn main:app --port 8000` after downloading the model folder from Drive.

## 6. Website behaviour

### Page structure (desktop ≥ 1024 px)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ Notes to Questions                                  API link from Colab      │
│ One-sentence description of what it does           [ https://…        ][Test]│
│                                                     ● Connected  model on gpu│
├──────────────────────────────┬──────────────────────────────────────────────┤
│ Your notes    Use sample notes│ Questions                       Download CSV │
│ ┌───────────────────────────┐ │ ┌──────────────────────────────────────────┐ │
│ │ ruled notebook textarea   │ │ │ 5 questions · 0.64 relevance · 4 of 5 …  │ │
│ │                           │ │ └──────────────────────────────────────────┘ │
│ │                           │ │ ┌──────────────────────────────────────────┐ │
│ └───────────────────────────┘ │ │ Q1  Question in serif                    │ │
│ 99 words      643 / 12,000    │ │     source sentence with ▇answer▇ marked  │ │
│ Questions ──●── 5  ☐ Quiz mode│ │     Relevance ▬▬▬▬▬▬  Correctness ▬▬▬▬▬  │ │
│ [ Generate questions        ] │ │     ( Relevant and answerable )          │ │
│  (sticky while results scroll)│ │ └──────────────────────────────────────────┘ │
└──────────────────────────────┴──────────────────────────────────────────────┘
```

Two columns at 5 : 7. The left column is sticky so the notes stay visible while scrolling questions. Below 1024 px everything stacks: header, API bar, notes, controls, results.

### User flow

1. **First visit.** The API field is empty. The results column shows the empty state (section 6, states).
2. **Connect.** User pastes the Colab link and presses **Test connection** (or Enter). Status dot: grey "Not checked" → amber "Checking…" → green "Connected" + model and device, or red "Not reachable" + the reason.
3. **Notes.** User types or pastes notes, or presses **Use sample notes**. A live counter shows words and characters out of 12,000.
4. **Settings.** Slider for 1–10 questions (default 5). **Quiz mode** checkbox (default off).
5. **Generate.** Button is disabled when notes are under 20 characters or over 12,000 (show a short hint below it in the first case). While running: button label changes to "Generating questions…", and the results column shows skeleton cards.
6. **Results.** A summary row, then one card per question in rank order.
7. **Quiz mode on.** Each card hides the answer highlight (replaced by a hatched block) and the scores. A **Show answer** button reveals them for that card only; it toggles to **Hide answer**.
8. **Download CSV.** Exports question, answer, source sentence, relevance, correctness, QA answer and verdict.
9. **Persistence.** The API link and the notes are remembered in localStorage (wrapped in try/catch; the page must still work when storage is blocked).

### States the results column must handle

| State | What to show |
|---|---|
| Empty (nothing generated yet) | Dashed outline box. One serif sentence explaining that each question will show its source sentence with the answer highlighted, using a real highlighter mark on the words "answer highlighted". One line of instruction below. |
| Loading | 1–3 skeleton cards with a gentle pulse (respect reduced motion). |
| Error | Red-tinted box, `role="alert"`, plain sentence that says what failed and how to fix it. |
| Results, 0 questions | Plain box: "No questions came out of these notes. Try longer notes with full sentences and named facts." |
| Results | Summary + cards. |

### Error messages (exact wording)

- No API link: "Add the API link from Colab first."
- Network failure: "Can't reach `<url>`. Check that the server cell is still running in Colab and the link is current."
- 422: join the validation messages into one sentence.
- Other non-OK: the server's `detail`, or "The API answered with status `<code>`."

Errors never apologise and never say "Oops".

### Question card anatomy

- Left: `Q1`, `Q2`… in small semibold muted type (it is a real sequence, so numbering is justified).
- Question: serif, about 22 px, the most prominent text on the card.
- Source sentence below it in serif, muted, with the answer wrapped in the **highlighter mark** (section 7). Match case-insensitively; if the answer isn't found, show the sentence plain.
- Two meters side by side (stacked on mobile): label, value to 2 decimals, a thin bar, and a one-line hint underneath.
  - Relevance hint: "How close the question is to this part of your notes"
  - Correctness hint: `A QA model answered "<qa_answer>"`
- Verdict pill at the bottom:
  - good → "Relevant and answerable" (green)
  - check → "Worth a second look" (amber)
  - weak → "Weak question" (red)

### Summary row

Four stats in a row (2 × 2 on mobile): number of questions · average relevance (2 decimals) · "4 of 5 answerable from notes" · generation time in seconds.

## 7. Visual design

### Concept

**A student's notebook page and a highlighter pen.** The notes box is ruled notebook paper with a red margin line. The answer the model was asked about is marked with a yellow highlighter stroke, which is exactly what the `<hl>` tokens do inside the model. The highlighter is the one memorable visual element; everything else stays quiet and disciplined.

### Colour tokens

| Token | Hex | Use |
|---|---|---|
| paper | `#F5F7FA` | page background (cool, not cream) |
| sheet | `#FFFFFF` | cards, inputs, notes box |
| ink | `#1C2541` | text, primary button, bars (navy ink, not black) |
| ink-soft | `#4A5571` | secondary text |
| rule | `#DBE5F1` | ruled lines, borders, empty bar track |
| margin | `#F2B8B5` | the notebook margin line |
| marker | `#FFE45C` | highlighter |
| good / check / weak | `#227A4F` / `#A8650F` / `#B23A33` | verdicts and status dots, used as text on a 10 % tint |

No gradients as decoration, no glow, no extra accent colours.

### Typography

- **Source Serif 4** for the page title, questions, notes text and source sentences: the "paper" voice.
- **Figtree** for the interface: labels, buttons, numbers, hints.
- Numbers use tabular figures.
- Sentence case everywhere. No all-caps labels, no eyebrow labels above headings, no single accented word in the title.
- Body line length under ~80 characters.

### Details

- **Ruled notes box:** horizontal lines every 32 px that line up with the textarea's line-height (scroll with the text), a 1 px margin line about 52 px from the left, text starting after the margin.
- **Highlighter mark:** yellow fill with slightly uneven, rounded edges (like a real marker stroke, not a flat rectangle), small horizontal padding, wraps correctly across lines.
- **Hidden answer (quiz mode):** a soft diagonal hatch block the same size as the answer, text transparent.
- **Cards:** white, 1 px rule border, 8 px radius, a very light shadow. Not every element gets a card: the header and the controls are not cards.
- **Motion:** one moment only. Result cards fade up with a 60 ms stagger when they arrive. Nothing animates on hover except colour. Respect `prefers-reduced-motion`.
- **Focus:** visible 2 px ink outline on every interactive element.
- **Favicon:** a small notebook page with a yellow highlighted line.

### Copy

Plain, active, user's point of view. The main button says **Generate questions** everywhere. "Test connection", "Use sample notes", "Download CSV", "Show answer" / "Hide answer". No "AI-powered", no "magic", no exclamation marks.

## 8. Accessibility and responsiveness

- Works from 360 px wide. No horizontal scroll.
- All inputs have labels. The results region is `aria-live="polite"`. Errors use `role="alert"`.
- Colour is never the only signal: verdict pills have text, status dots have text next to them.
- Contrast AA for all text.

## 9. Build order (milestones)

Build in this order and check each milestone before moving on.

1. **Mock API.** A tiny FastAPI (or Express) server in `web/mock/` that implements section 4 with fixed, realistic sample questions and a 1-second delay, including one `weak` and one `check` question. This lets the whole UI be built without the model.
2. **Website skeleton.** Layout, design tokens, fonts, header, API bar, notes box, controls. No results yet.
3. **Results.** Summary, question cards, highlighter, meters, verdicts, empty / loading / error states, wired to the mock API.
4. **Quiz mode, CSV, localStorage.**
5. **Real API.** `api/` with the pipeline in section 5. Test it locally on CPU against the fine-tuned model folder, then through `run_colab.ipynb`.
6. **Switch the website to the real API.** Only the URL changes.
7. **README** with the exact run steps for Colab and for the website.

## 11. Demo script (about 3 minutes)

1. Show the Colab notebook briefly: fine-tuning loss curve and the baseline vs fine-tuned results table.
2. Open the website, paste the Colab link, Test connection (green).
3. Press **Use sample notes** → Generate. Point at one card: the highlighted answer, the question, both scores, the verdict.
4. Paste a paragraph from a different subject → Generate, to show it works on any notes.
5. Turn on **Quiz mode** and reveal one answer.
6. Point out one **weak** question honestly and explain why its scores are low: that is the evaluation doing its job.

## 12. Known limits (keep visible in the README and slides)

- English notes only (the model was trained on English SQuAD).
- Mostly factual what / when / who questions; rarely "why" or "explain".
- Works best on full sentences; bullet-point fragments give weaker questions.
- The free Colab session and the tunnel link expire; the link changes on every restart.
